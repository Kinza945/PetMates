# PetMates: анализ готовности Android-приложения к релизу

Дата анализа: 2026-04-26

## Кратко

PetMates задуман как платформа для поиска команды под pet-проекты. По документу продукт должен иметь Web и Mobile клиенты, общую REST API-логику, Supabase/PostgreSQL в качестве БД и сценарии вокруг пользователей, проектов, вакансий, откликов, приглашений и уведомлений.

Текущий репозиторий содержит Android-клиент. Web-клиента в кодовой базе не обнаружено, поэтому ниже анализируется именно мобильная часть. По состоянию Android-клиента: проект уже выглядит как рабочая mock-версия и хорошо подготовлен архитектурно, но до релиза не хватает настоящего API/Auth, серверных правил, удаления сущностей, полного тестового покрытия и финального UI-polish.

Оценка готовности:

- Mock/MVP для демонстрации: 75-80%.
- Готовность к подключению API: 70-75%.
- Готовность к публичному релизу: 45-55%.

## Что уже сделано

### Архитектура

- Проект разделён на `domain`, `data`, `app`.
- `domain` содержит сущности и контракты репозиториев.
- `data` содержит mock-репозитории, real-репозитории, Ktor/Supabase transport.
- `app` содержит Compose UI, ViewModels, Hilt DI и навигацию.
- Есть `USE_MOCKS`, позволяющий переключать mock/real реализации.
- UI постепенно переводится на MVVM, UDF, `StateFlow` и one-shot events.

### Авторизация и сессия

- Добавлен `AuthRepository` в `domain`.
- Есть `MockAuthRepository`.
- Сессия сохраняется через `SharedPreferences`.
- `SessionManager` стал единым источником auth-состояния.
- Есть guest-режим.
- Есть logout flow с подтверждением.
- Есть общий `AuthRequiredScreen`.

### Данные и API-ready слой

- Есть модели для основных таблиц: users, projects, vacancies, responses, invites, notifications.
- Есть DTO и JSON helpers для Supabase.
- `SupabaseRestApi` поддерживает `GET`, `POST`, `PATCH`, `DELETE`.
- Ktor client готов добавлять `apikey` и будущий Bearer JWT.
- Real-репозитории частично реализованы для CRUD.
- Mock-репозитории реализуют важные бизнес-правила:
  - запрет повторного pending-отклика;
  - запрет отклика автора проекта на свою вакансию;
  - запрет отклика участника проекта;
  - отмена отклика;
  - запрет повторного приглашения;
  - отмена приглашения;
  - unread count уведомлений;
  - оценка проекта один раз на пользователя.

### UI и сценарии

- Есть экран авторизации/регистрации.
- Есть главный экран с нижней навигацией.
- Есть мероприятия/лента проектов.
- Есть участники.
- Есть заявки.
- Есть уведомления.
- Есть профиль текущего пользователя с данными из mock-репозитория.
- Есть чужой профиль.
- Есть редактирование профиля.
- Есть создание проекта.
- Есть редактирование проекта.
- Есть детали проекта.
- Есть создание вакансии.
- Есть редактирование вакансии.
- Есть детали вакансии.
- Есть приглашение пользователя в проект.
- Настройки перекомпонованы в карточки: аккаунт, уведомления, безопасность, опасная зона.

### Тесты и сборка

- Есть unit-тесты mock-репозиториев.
- Есть тесты mock-auth.
- Есть UI smoke-тесты для части экранов.
- Проверки проходили:
  - `:data:test`
  - `:app:assembleDebug`
  - `:app:assembleDebugAndroidTest`

## Что не хватает до релиза

### Блокирующее

1. Настоящая Supabase Auth
   - login/register через Supabase Auth;
   - refresh token;
   - восстановление JWT;
   - безопасное хранение токенов;
   - logout с реальной очисткой сессии.

2. Реальные backend/RPC правила
   - отклик/приглашение/оценка проекта должны проверяться сервером;
   - уведомления должны создаваться сервером, а не только клиентом;
   - `rateProject` требует RPC или Edge Function;
   - принятие отклика/приглашения должно быть защищено правами владельца.

3. Supabase RLS policies
   - кто может читать/писать users;
   - кто может создавать проекты/вакансии;
   - кто может принимать/отклонять отклики;
   - кто может читать уведомления;
   - запрет записи чужих данных.

4. Удаление сущностей
   - удаление аккаунта;
   - удаление проекта;
   - удаление вакансии;
   - удаление уведомления;
   - каскадное удаление/уведомления по правилам из документа.

5. Полная проверка `USE_MOCKS=false`
   - dev Supabase база;
   - реальные env-переменные;
   - прогон CRUD-сценариев на реальном backend.

### Важно, но не блокирует MVP

- Pull-to-refresh на списках.
- Пагинация/фильтры с сервера.
- Empty states для всех списков.
- Красивые error states с retry.
- Badge непрочитанных уведомлений в TopBar с real count.
- Единая дизайн-система для всех экранов.
- Полный переход старых ViewModels на `StateFlow`.
- Больше UI-тестов навигации.
- Unit-тесты новых ViewModels.
- Обработка offline/network timeout.
- Логирование без утечки токенов.
- Crash reporting.

## Соответствие документу

### Хорошо совпадает

- Роли guest/authorized частично реализованы.
- Основные таблицы отражены в domain/data.
- Основные окна Android реализованы или есть mock-версии.
- Отклики привязаны к вакансиям.
- Приглашения существуют отдельно от откликов.
- Уведомления имеют категории и reference-ссылки.
- Нижняя навигация соответствует идее: профиль, мероприятия, заявки, участники.
- Mock-логика покрывает многие сценарии из раздела "ТЕСТИРОВАНИЕ".

### Частично совпадает

- Модератор/owner роли есть в моделях, но UI/сценарии модерации не реализованы.
- Удаление аккаунта есть как UI-заглушка, но нет реальной логики.
- Удаление проекта/вакансии/участника не реализовано.
- Фильтры и сортировки реализованы частично.
- Уведомления можно читать/удалять частично, но нет фильтров по проекту/участнику.
- Иконки частично используются, но нет полноценного подключения всех assets из документа.

### Не реализовано

- Web-клиент.
- REST API backend.
- Supabase Auth в real-режиме.
- Realtime-уведомления.
- Модераторская форма.
- Бан пользователей.
- Админ/owner управление ролями.
- Beta feedback/bug-report раздел.
- Полноценная система удаления и каскадных уведомлений.
- Мониторинг, метрики, production logging.

## Рекомендованный план до релиза

### Этап 1. Закрыть API/Auth foundation

- Подключить Supabase Auth.
- Настроить secure token storage.
- Завести dev Supabase проект.
- Проверить таблицы, enum, jsonb форматы.
- Написать RLS policies.
- Прогнать приложение с `USE_MOCKS=false`.

### Этап 2. Закрыть серверные бизнес-операции

- RPC/endpoint для `rateProject`.
- RPC/endpoint для принятия/отклонения отклика.
- RPC/endpoint для приглашений.
- RPC/endpoint или DB triggers для уведомлений.
- Endpoint/RPC для "мой профиль с активностью", чтобы не собирать это клиентом через много запросов.

### Этап 3. Довести пользовательские сценарии

- Удаление аккаунта.
- Удаление проекта.
- Удаление вакансии.
- Удаление уведомлений.
- Управление участниками проекта.
- Редактирование роли участника.
- Полная история уведомлений с фильтрами.

### Этап 4. UI/UX polish

- Единые loading/error/empty states.
- Скелетоны на списках.
- Pull-to-refresh.
- Badge уведомлений.
- Финальная настройка отступов и карточек.
- Подключение финальных SVG-иконок.

### Этап 5. Тестирование

- Unit-тесты всех ViewModels.
- MockEngine tests для real repositories.
- UI smoke tests основных сценариев:
  - регистрация/вход/выход;
  - guest restrictions;
  - создание/редактирование проекта;
  - создание/редактирование вакансии;
  - отклик/отмена отклика;
  - приглашение/принятие/отклонение;
  - уведомления/read all/delete.
- Ручной регресс по чек-листу из документа.

## Основные риски

- Без RLS и серверных правил клиентские проверки нельзя считать безопасными.
- `rateProject` и создание уведомлений нельзя надёжно делать только на клиенте.
- Текущий профиль активности собирается клиентом через обход проектов/вакансий; на реальном API это может стать медленно.
- Удаление сущностей требует аккуратных каскадов и уведомлений.
- Web часть описана в документе, но отсутствует в текущей кодовой базе.

## Итог

Android-клиент уже является хорошей mock-версией для демонстрации идеи PetMates и подготовки к API. Архитектура в целом выбрана правильно: domain-контракты, data-реализации, mock/real переключение, ViewModels и Compose UI. Для релиза главный фокус должен быть не на добавлении новых экранов, а на подключении настоящего backend/Auth, RLS, серверных бизнес-операциях и тестировании сценариев из документа.
